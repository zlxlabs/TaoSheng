# 卡 185b 交付说明：屏幕时间采集底座

## 做了什么

**数据库（34 → 35）**
- `CaptureDatabase.VERSION` 34 → 35，迁移只有 `MIGRATION_34_35` 一条，登记在 `MIGRATIONS` 末尾；schema 导出 `shared/schemas/app.resound.data.CaptureDatabase/35.json`。
- 四张新表（实体与 DAO 都在 `:shared` 的 `app.resound.screentime` 包）：
  - `screen_events`：唯一索引（at,pkg,type,cls），插入冲突忽略；`type` 只收九种（1、2、23、15、16、17、18、26、27），拉取时过滤，未知类型丢弃；空类名存空串。
  - `screen_app_names`：包名主键 + 显示名 + updatedAt。
  - `screen_pull_state`：source 主键（本卡只用 `'screen'`）、coveredUntil（可空）、floor（默认 0）。
  - `screen_coverage_gaps`：索引（source,fromAt）；落库的 code 只有 `pull_failed` 和 `disabled` 两种（本卡范围内），`coverage_lag` 按卡面只在查询时现算。
- `ScreenTimeDao`：卡 186 消费的四个读方法签名与卡面一致；写入侧的事务封装成 `@Transaction` 方法 `commitPull`（事件+名称+覆盖指针同事务，失败整体回滚）和 `advanceCoveredUntil`（覆盖指针只增不减）。MAX 语义用「INSERT IGNORE 首建 + UPDATE MAX」两段式，不用 `@Upsert`（那会整行覆盖、丢 floor）。

**总开关与拉取器（`:shared`）**
- `ScreenTimeSettings`：键 `screenTimeEnabled`，默认关；写法照 `DigestPreferenceStore`，成功提交后才发布 StateFlow。从关到开时通知装配层（`onReenabled`），由装配层异步查覆盖进度、补记 `disabled` 缺口（见下方「与卡面的偏差」第 1 条）。
- `ScreenTimePuller.pull()`：全程一把 `kotlinx.coroutines.sync.Mutex`（AppGraph 装配为单例，周期任务与查询前拉取共用）；关闭→`Disabled`（不碰事件源任何方法）；无授权→`NoPermission`；30 秒内重复拉→`Throttled`；起点 `max(表内最大 at, coveredUntil, floor, 此刻−10天)`；停采超 10 天先落 `pull_failed` 缺口（[旧 coveredUntil, 此刻−10天)）；事件、名称、coveredUntil=此刻 同事务写入，零事件也推进覆盖指针；`SecurityException`→`NoPermission`、其他异常→`Failed(异常类名)`，取消异常原样上抛。
- 日志前缀 `screentime:`，只记数量、原始条数、耗时、异常类型，不记包名与时间线。

**安卓侧（`app/`）**
- `AndroidScreenEventSource`：授权判断直接复用 `MicHolderGuess.permitted()`（组合实例，不复制逻辑）；`PACKAGE_USAGE_STATS` 在 Manifest 已声明，未改动。
- `ScreenTimePullWorker`：周期任务名 `screen-time-pull`，1 小时；`Failed` 时 `runAttemptCount < 3` 重试、否则失败；`Disabled`/`NoPermission`/`Throttled` 均按 success。
- `ResoundApp` 装配：开关存 `screen-time` SharedPreferences；开关打开时排定周期任务、关闭时取消；拉取器单例挂在 `AppGraph.screenTimePuller`（另有 `screenTimeSettings`、`isScreenTimeReady`）。

**删除与备份**
- `RoomPrivacyActions.deleteRange` / `deleteRecent`：在原有同一 Room 事务内追加删 `screen_events` 区间行，并把 `'screen'` 的 floor 提到 `max(floor, 区间终点)`；按事件/按段的遗忘不受影响。
- `DayVolumeRows`：`dated` 登记 `"screen_events" to "at"`；`global` 登记 `screen_app_names`、`screen_pull_state`、`screen_coverage_gaps`。恢复收尾在 `DayVolumeRows.rebuild` 的事务内（分卷恢复 `restoreVolumes → DayVolumes.restore → rebuild` 的终点）：`UPDATE screen_pull_state SET coveredUntil = COALESCE((SELECT MAX(at) FROM screen_events), coveredUntil) WHERE source = 'screen'`，状态卷比事件卷新时不会产生假覆盖。

## 真机需要注意什么

1. **真机验收（本卡完成条件）**：升级安装 → 总开关默认关（确认设置项默认值）；打开总开关 → 授权「使用情况访问」→ 等 1 小时后查 `screen_events` 有行；关闭总开关 → 不再新增；删除最近 1 小时 → 再拉取，被删行不回来。
2. **连续 3 天记录日均行数**（给卡 186 定容量预期）。
3. 小米 14 Pro（澎湃 OS）的「使用情况访问」授权入口有时会自动回弹，若 `permitted()` 为 false 拉取返回 `NoPermission`，需重新授权。
4. 恢复备份后 `coveredUntil` 重置为表内最大事件时刻：可验一次「备份 → 抹数据 → 恢复 → 开关打开后能补拉最近事件」。

## 遗留问题与偏差声明

1. **与卡面锁定的偏差（settings）**：卡面写「从关到开且该来源已有 coveredUntil 时写一条 disabled 缺口」。实现上 `ScreenTimeSettings.setEnabled` 是非 suspend 接口，查覆盖进度是 suspend DAO 调用，二者不能同栈。落地为：`setEnabled` 只在「关→开」转变时通知 `onReenabled` 回调，「查 coveredUntil、判断非空且小于此刻、写 disabled 缺口」由装配层在 `scope.launch` 里异步完成。语义等价，但缺口写入是异步的：极端情况下开开关后立刻杀进程，那条 disabled 缺口会丢（不影响已采数据，只少一条空档留痕）。shared 测试只验证「关→开通知次数」，coveredUntil 判断部分由真机验收覆盖。
2. **PullResult.Pulled 的 count 是「过滤后事件条数」**，不是新增行数：重复拉取同一批时返回 `Pulled(3)` 但行数不变（冲突忽略）。诊断日志同样记这个数。卡 186 若要「新增行数」需另查。
3. 节流时间戳（`screenTimeLastPullAt`）存 SharedPreferences 而非数据库——`screen_pull_state` 表结构被卡面锁定不能加列，且节流判据属进程内状态，不需要跨设备恢复。备份恢复后节流时间戳跟随本机设置，不随备份走。
4. `ScreenTimeConfig().pullThrottleMillis`：185a 尚未合并，30 秒常量先写在 `ScreenTimePuller.PULL_THROTTLE_MILLIS`，185a 合并后改引用（卡面已注明）。
5. shared jvmTest 无 Room 测试设施（无 `sqlite-bundled` 依赖），`ScreenTimeDao` 的 jvmTest 用内存假库实现同一接口（含 `@Transaction` 语义的「先校验后落盘」模拟）；真库行为由 app 侧 Robolectric 测试（真 SQLite）覆盖。
6. 本卡未实现卡 186 的查询、185a 的使用段计算；`coverage_lag` 只在查询时现算的规则留给消费卡。
