# 卡 191a 交付说明：外放片段「仍要转写」后暂不整理（数据层）

## 做了什么

「仍要转写」的外放片段现在转写行照常保存（可搜、可问），但默认不进整理；用户放行（`allowPlaybackDigest`）后才参与之后的整理。拦截点放在「取待整理行」的查询上，一处拦截对整理、寻物提取、待办完成线索、缓存的整理回复全部生效。

- `SegmentEntity` 新增 `playbackDigest: Int = 0`：`0` 正常；`1`「仍要转写」的外放片段（暂不整理）；`2` 用户已放行。注释写在实体字段上。
- `CaptureDatabase.VERSION` 36 → 37；`MIGRATION_36_37`（`ALTER TABLE segments ADD COLUMN playbackDigest INTEGER NOT NULL DEFAULT 0`）登记在 `MIGRATIONS` 末尾；导出 `shared/schemas/app.resound.data.CaptureDatabase/37.json`（identityHash `c4833f8c0c29b234f112233f5a7c9b48`）。
- `TranscribeDao.transcribeAnyway`：`UPDATE` 同时写 `playbackDigest = 1`（原 `status = 'SkippedPlayback'` 条件不变）。
- `TranscribeDao.allowPlaybackDigest(id)`：`UPDATE segments SET playbackDigest = 2 WHERE id = :id AND playbackDigest = 1`；`TranscriptStoreRepository.allowPlaybackDigest` 在 `scope.launch` 里调用，不触发整理。
- `TranscriptStoreRepository.day()`：构造 `SegmentTranscript` 传 `playbackHeld = segment.playbackDigest == 1`。
- 卡 183 冻结夹具白名单（`index183/expected-delta.json`）按 190a/185c 同一写法登记 37 版差异；比较器 `Index183FixtureDelta` 新增 `columnAdds` 规则（见下「夹具」）。

## 取待整理行的取数口清单（卡面要求逐项列出）

grep 了整个 `shared/src/commonMain` 与 `app/src/main/java` 的 `digestedAt IS NULL`：

| 取数口 | 是否加 `s.playbackDigest != 1` | 说明 |
|---|---|---|
| `MemoryDao.undigestedLines`（115 行） | 加 | 整理取行主查询 |
| `MemoryDao.undigestedCount`（121 行） | 加 | 整理计数 |
| `MemoryDao.observeUndigestedCount`（138 行） | 加 | 界面角标/自动整理唤醒 |
| `TopicData.observeLateTranscriptIds`（约 59 行） | 不加 | 专题补整理的**唤醒判断**，非整理取行：它只判定专题时段内有没有「未归事件的原话」来决定是否触发专题整理，真正取行走 topic_spans 时间窗；被拦片段的行 `digestedAt IS NULL` 会参与该判断，但专题整理取行时不把它当素材整理进事件（见下方遗留第 3 条） |
| `VoiceInputDao`（语音输入纠正，26 行） | 不加 | 改写文本的 UPDATE 条件，与整理无关 |
| `TopicData.digestedUntil` | 不加 | 只取 `digestedAt IS NOT NULL` 的已整理行，方向相反 |

全仓没有其他「`digestedAt IS NULL` 且 `s.status = 'Done'`」的取数口。寻物提取、待办完成线索、缓存的整理回复都经由 `undigestedLines` 或其行集（`PendingDigest.ids()` 即其产物），拦截生效。

## 夹具（index183 白名单）

37 版与之前升版不同：`segments` 是**已存在表加列**，sqlite_master 的 CREATE TABLE 行、`TABLE segments` 块的 `columns=` 行、每条数据行尾都会变，而且旧行/新行文本随快照的建库方式（Room 新装 vs 从 1/33 起迁移累积 ALTER）各有多种形态。白名单机制原有四类（版本行、身份行、新索引、新表）覆盖不了，按 185c「扩展 `Index183FixtureDelta` + 逐字登记」的路子新增 `columnAdds` 规则：

- **master 行**：旧行从各快照的旧夹具现取（不枚举 34 种形态），断言新行必须等于「旧行在最后一个列定义后插入迁移片段」（程序化与 `CaptureDatabase.MIGRATIONS` 里登记的 `ALTER` SQL 同源拼校验）**或**等于 `masterFreshLine`（37 版 Room 新装形态，从 `37.json` createSql 同构核对）。验证过 33→36 的历史 ALTER 不改 segments 文本，所以 36 新装与 33 起迁移的旧行文本相同，映射到两个不同新行——候选数组语义由此而来。
- **columns 行**：旧行逐字 → 新行逐字（`...,"speakerCount","playbackDigest"]`）。
- **数据行**：每行必须以 `,{"integer":0}` 结尾（新列默认值 0），去尾后与旧行 multiset 相等——旧行文本逐字锁定。
- `version.newLine` = `user_version=37`；`identity.newRow`/`newIdentityHash`/`newSetupQueries` 哈希与 `37.json` 一致。旧版本（33-36）登记的行全部保留。
- `Index183ComparatorTest.allowed()` 同步按 `columnAdds` 构造合法输入；`Index183MigrationTest` 的幂等重放改为：历史段（33→36，全 IF NOT EXISTS）对已升级库重复重放两遍，36→37 的 `ALTER ADD COLUMN` 无 `IF NOT EXISTS`（SQLite 不支持）不可重放，其单次真实执行由测试内的 Room open 覆盖。

行均从重放输出提取、与 `37.json`/迁移 SQL 逐字核对后写入，不由测试运行时自动生成。

## 备份与恢复

核实结论：备份是**物理快照**（`BackupArchive.snapshot` 复制 db 文件 + `logicalSnapshot` 整表复制），**没有逐列列举 `segments`**，本卡未改任何备份代码。旧备份（低版本）`verify` 允许 `sourceVersion ≤ 37`，恢复时 `CaptureDatabase.open` 自动跑 `MIGRATION_36_37`，恢复后片段的「暂不整理」状态（=1）在物理快照里原样保留，不丢。

## 遗留与真机注意

1. 卡 191b（界面）：放行按钮、「不参与整理」标识依赖 `SegmentTranscript.playbackHeld` 与 `TranscriptRepository.allowPlaybackDigest`，签名未动。
2. 放行后不主动触发整理（契约如此）：自动整理定时或用户「现在整理」时该片段行才被 `undigestedLines` 带出。
3. 专题（topic）时段与外放片段重叠时，`observeLateTranscriptIds` 的唤醒判断会看到这些行（`digestedAt IS NULL`）；专题整理取行按 topic_spans 时间窗且归入专题自己的事件，若负责人希望外放节目原话也不进专题整理，需要后续卡在专题取行查询同样加 `!= 1`（本卡按卡面「取待整理行」口径执行，专题取行不属于该口径）。
4. 37.json 为 Room 自动导出（3141 行），diff 超预算部分几乎全来自该生成物，190a 的 36.json（3134 行）同例。
