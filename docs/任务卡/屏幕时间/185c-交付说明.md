# 卡 185c 交付说明：数据库 35 版的夹具差异登记

## 做了什么

把 185b 升级（33→35，新增 `screen_events`、`screen_app_names`、`screen_pull_state`、`screen_coverage_gaps` 四张表及索引）带来的**精确**结构差异登记进卡 183 的白名单机制，修复 CI 上 `:app:testDebugUnitTest` 的 11 个失败（run 43592319856）。不改任何产品代码，不动 `driver175/` 夹具与 `manifest.json`。

### 白名单写法：选方案 (a)

沿用并推广 `app/src/test/resources/index183/expected-delta.json`，口径从「33→34」推广为「33→`CaptureDatabase.VERSION`」。理由：

- `Index183FixtureDelta.assertSame` 里已有硬断言 `assertEquals("user_version=${CaptureDatabase.VERSION}", version.newLine)`，JSON 的 newLine 天然被钉在当前版本上；方案 (b) 叠加文件会让「当前版本」的定义分散在两处，还需要引入叠加顺序概念。
- 单文件单口径，183 交付说明「比较器先断言每项旧值、新值和精确次数，再只还原这些白名单行」的叙述继续成立，不需要新文档解释两层结构。

### 逐条新增的允许差异（全部逐字精确，无前缀/通配）

1. **版本行**：`user_version=34` → `user_version=35`（各快照首行，1 次）。
2. **身份行**：room_master_table 的 id=42 行哈希 `c8d36ea3...`（34）→ `fe863c01282120a32fb7708de4818567`（35，与 `shared/schemas/app.resound.data.CaptureDatabase/35.json` 的 `database.identityHash` 一致），旧哈希 `c8e25a89...`（33 夹具）不变。
3. **sqlite_master 新增索引行 4 条**（`indices` 数组追加，各出现 1 次）：
   - `index_screen_events_at_pkg_type_cls`（UNIQUE，`screen_events`）
   - `index_screen_coverage_gaps_source_fromAt`（`screen_coverage_gaps`）
   - `sqlite_autoindex_screen_app_names_1`（TEXT 主键自动索引，SQL 为 null）
   - `sqlite_autoindex_screen_pull_state_1`（同上）
   
   （34 版已有的 `index_segments_status_voiceprintProcessedAt`、`index_transcript_lines_startAt` 两条保持不变。）新增项不带 `schemaIndex` 字段——该字段在测试代码中零消费者，仅 183 的一次性核验脚本 `tools/index-audit-183/verify.py` 用过。
4. **新增表块 4 项**（JSON 新增 `tables` 数组，`Index183FixtureDelta.assertSame` 同样先断言精确次数再移除）：
   - 每项含 `masterRows`（sqlite_master 表行的**候选数组**）、`block`（数据块三行：`TABLE <表名>` 行、`columns=[...]` 行、空行）、`occurrences: 1`。
   - 候选数组的原因见下节「两路径形态差异」；`screen_coverage_gaps` 两路径文本相同，候选只有 1 条。
   - 表行候选总数精确断言为 1：同一快照里两种形态各出现一次会被拒绝，出现候选之外的未知表行由最后的逐字比较拒绝。

新增行均先从重放输出提取、再与 `35.json`（identityHash、四张表 createSql、两条显式索引）和 `CaptureDatabase.MIGRATION_34_35` 手写 SQL 逐字人工核对后写入，不由测试运行时自动生成。

## 必须显式提出的发现：35 版两路径 sqlite_master 文本不同

同一张新表，Room 新装（按 `35.json` 实体 createSql）与迁移（按 `MIGRATION_34_35` 手写 SQL）写入 sqlite_master 的 SQL 文本**不完全一致**，共三处：

| 表 | 新装形态 | 迁移形态 |
|---|---|---|
| screen_app_names | `pkg TEXT NOT NULL, ..., PRIMARY KEY(\`pkg\`)` | `pkg TEXT NOT NULL PRIMARY KEY, ...` |
| screen_events | `cls TEXT NOT NULL` | `cls TEXT NOT NULL DEFAULT ''` |
| screen_pull_state | `floor INTEGER NOT NULL` | `floor INTEGER NOT NULL DEFAULT 0` |

`screen_coverage_gaps` 两路径文本相同。Room 只按 `PRAGMA table_info` 校验结构，不比对 SQL 文本，所以两条路径都合法、identityHash 相同。这不是 bug，但属于 185b 迁移语句与实体定义不逐字一致的既有事实，本卡不改产品代码，只在白名单里如实登记两种形态，并在此显式提出，供 185b 负责人决定是否统一。

由此对测试做了两处调整：

1. `Index183FixtureDelta`：`tables` 项从单行 `masterRow` 改为候选数组 `masterRows`（断言候选总次数精确等于 occurrences，然后移除出现的那一条）。
2. `Index183MigrationTest.realRoomMigrates33...` 里的 `assertEquals(structure(fresh), structure(db))`：`structure()` 原来返回 sqlite_master 四列（含 SQL 文本），35 版两路径文本有上表差异，逐字比较必然失败。改为返回前三列（type/name/tbl_name）对象清单做断言；**精确性无损失**——迁移路径完整文本由 `backup-before.txt` 等快照经白名单逐字锁定，新装路径由 `fresh-install.txt` 逐字锁定，双覆盖各自独立存在。

另外 `Index183MigrationTest` 里 `MIGRATIONS.single { startVersion==33 && endVersion==VERSION }` 在 35 版下找不到对象（33→35 现在是 33→34→35 两段），改为取 `startVersion>=33 && endVersion<=VERSION` 的链，并断言链长等于 `VERSION-33`（版本连续无缺口）；重复执行两遍验证幂等的语义不变。写死 33 的「旧备份来源版本」断言按卡面保持不变。

## 遗留与提醒

- `tools/index-audit-183/verify.py`（183 的一次性核验脚本）写死 34 口径（`len(spec['indices'])==2`、`version:[33,34]`），在 35 版下重跑会失败。它是历史证据工具，不在本卡修改边界，未改动；其结论已固化在 183 交付说明与证据目录里。

## 以后再升数据库版本（36 及以后）要改哪些地方

1. `app/src/test/resources/index183/expected-delta.json`：
   - `version.newLine` 改为 `user_version=<新版本>`（比较器会自动校验它与 `CaptureDatabase.VERSION` 一致，忘改必红）；
   - `identity.newRow`、`newIdentityHash`、`newSetupQueries` 的哈希改为新版本 `shared/schemas/app.resound.data.CaptureDatabase/<新版本>.json` 里 `database.identityHash`；
   - 新版本新增的索引：在 `indices` 数组逐条追加完整 sqlite_master 行（含 UNIQUE 前缀与反引号原文；TEXT 主键自动索引也要登记，SQL 为 null）；
   - 新版本新增的表：在 `tables` 数组追加，`masterRows` 登记迁移与新装两条形态（文本一致就一条），`block` 登记三行数据块（TABLE 行、columns 行、空行）；
   - 旧版本（34、35）登记过的行**全部保留不动**。
2. 若新版本也存在「迁移手写 SQL 与实体 createSql 文本不一致」，`Index183MigrationTest.structure()` 的对象清单口径可继续用，不用改；若两路径文本完全一致，也不需要恢复四列比较（清单口径持续有效）。
3. `Index183MigrationTest` 里写死 33 的「旧备份来源版本」断言永远不动；迁移链断言 `VERSION-33` 自动适应。
4. `Driver175FixturesTest` 不需要动（全部走 `CaptureDatabase.VERSION` 与白名单）。
5. 改完做一次反例自检：删掉任一条新版本新增行，确认对应测试变红，再恢复。
6. 若某次升级没有表/索引变化（只有数据或哈希变化），只改版本行与哈希三处即可，`indices`/`tables` 不动。
