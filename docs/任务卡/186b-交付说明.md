# 卡 186b 交付说明：问问工具 apps_during

## 做了什么

问问新增工具 `apps_during`，按时间段查手机 App 使用时长，只通过约定接口 `ScreenTimeReader` 取数（本卡不实现读取器）。

1. **工具定义**（`AskDefinitions.kt`）：名称 `apps_during`；必填参数 `from`、`to`（`YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm`）；描述「查某段时间手机上用了哪些 App、各用多久；只有开启屏幕时间时才有数据」。
2. **进度文案**（`AskEngineCore.kt`）：`apps_during` →「正在查手机使用记录…」。
3. **共用实现**（`AskScreenToolsCore.kt`）：
   - 用 `AskTime.timestamp(from, false)` / `timestamp(to, true)` 转成左闭右开毫秒；`to <= from` 或跨度超过 10 天时抛 `AskDateException`，在调用 `reader()` 之前拒绝。
   - `reader()` 为 null 或 `enabled = false`：只返回空列表加 notice「屏幕时间未开启，没有 App 使用数据。」，不登记出处。
   - 正常输出字段顺序固定：`totals`、`sessions`、`devicePlayback`（本卡恒为空数组）、`coverageUntil`、`gaps`、`truncated`。
   - `totals` 按包名汇总后四舍五入到整分钟，时长降序、同时长按包名升序，一律完整给出。
   - JSON 超过 6000 字符时从尾部去掉 `sessions` 并置 `truncated = true`。
   - 每条 totals 和留下的 sessions 登记 `AskSource(kind = "screen", id = 段起点毫秒, …)`，`ref` 复用 `sources.indexOf` 去重。
4. **安卓装配**（`AndroidAskRepository.kt`）：`name == "apps_during"` 走 `AskScreenToolsCore({ AppGraph.screenTimeReader }, 系统时区)`，其余仍走 `placeTools.execute`。

## 需要界面配合的点

- 出处 `kind = "screen"` **不能跳转原话**（没有 line/event id），请按不可点击展示；标题是「\<App 名\> 使用」，quote 是「HH:mm–HH:mm \<App 名\>」。
- 出处列表里 `kind = "screen"` 的展示由界面卡处理。

## 追问时 `screen` 出处核验返回 null 的后果

`AskContext.kt` / `AskContextReader.refresh` 只认识 `line` / `event` / `item`，`kind = "screen"` 走 `else -> return null`。

追问 `followUp` 会跳过这些出处，不进入本轮资料。引擎拼历史时，上一轮带 screen 出处的助手回答会因「重新核验的 quote 对不上」被整段丢掉，不能当证据。用户追问 App 使用必须再调一次 `apps_during`。本卡按非目标不接预查询、不改 refresh。

预查询模式（`AskMode.Prefetch`）也不覆盖屏幕时间问题：程序先查的路径不会调 `apps_during`。

## 真机需要注意什么

- 本卡不实现 `ScreenTimeReader`（卡 186a）。reader 未装配时工具返回「屏幕时间未开启」notice，与总开关关闭相同。
- 总开关打开且 186a 接上之后，才有 totals/sessions；未授使用情况访问时列表为空、`gaps` 带 `usage_access_missing`。

## 遗留问题

- `devicePlayback` 本卡恒为空数组，第 3 步再填。
- 不接 `AskMode.Prefetch`；屏幕时间相关问题在预查询模式下仍可能答不出。
- 截断只砍 `sessions`，`totals` 一律完整；若包名极多导致 totals 单独超过 6000，JSON 仍会超标（卡面要求 totals 不砍）。
